# Slimefun Legacy 4.1.75 — Atomic Backpack Saves & Doctor Safety

Slimefun Legacy **4.1.75** is a focused storage-safety maintenance release. It
supersedes 4.1.74 when installed from the official versioned release. The published 4.1.74
binary contains the interrupted within-backpack save defect reproduced in
[#390](https://github.com/wickidcow/Slimefun-Legacy/issues/390); 4.1.75 contains the
transactional repair described below. Development builds and Actions artifacts are not
official releases. Installing or reading these notes does not itself change live server,
player inventory or production database data.

## Core changes since the published 4.1.74 JAR

- [#391](https://github.com/wickidcow/Slimefun-Legacy/pull/391), merged as
  `88e0b1e416c473485b2912dfe8413780d625a169`: one backpack's changed inserts,
  updates and deletions use one already-serialized immutable batch and one JDBC
  transaction. A two-slot move must persist the complete old or new state, not half
  a move. This fixes the controlled reproduction that recovered 69 or 23 items
  instead of the intended 46 after an abrupt process stop.
- [#387](https://github.com/wickidcow/Slimefun-Legacy/pull/387) separately protects the
  internal save chain by returning a detached completion future. A caller completing,
  cancelling or otherwise changing its returned future can no longer clear the internal
  persistence barrier while a database write is pending. Cancelling that observation
  does not cancel an accepted write. This is a production lifecycle fix, not test-only work.
- Per-backpack save ordering, incomplete-load save holds, original item serialization
  and uncertain-commit recovery are retained. Failed or uncertain saves are not
  acknowledged as successful, and unsupported adapters do not silently revert to
  independent per-slot writes.
- Doctor [#382](https://github.com/wickidcow/Slimefun-Legacy/pull/382) resolves each
  provider's display name once per listing before sorting instead of repeatedly invoking
  addon callbacks inside the comparator. [#383](https://github.com/wickidcow/Slimefun-Legacy/pull/383)
  rechecks plugin enablement at callback boundaries; [#384](https://github.com/wickidcow/Slimefun-Legacy/pull/384)
  also checks exact live service-registration identity, including status-name lookups.
  Disabled, withdrawn or replaced providers are not reused. These are command-time
  lifecycle safeguards, not an arbitrary asynchronous service-manager atomicity guarantee.
- Test-only [#385](https://github.com/wickidcow/Slimefun-Legacy/pull/385) and
  [#389](https://github.com/wickidcow/Slimefun-Legacy/pull/389) extend mixed-format loading
  and separate-process persistence coverage. #387 adds real-writer regressions alongside
  its production fix; #391 adds conserving multi-slot interruption and transaction tests.
- CI-only [#388](https://github.com/wickidcow/Slimefun-Legacy/pull/388) pins reviewed
  WorldEdit test dependencies after upstream download failures. It does not replace
  WorldEdit on a user's server or modify addon source selections. The existing 26.3
  test dependency is explicitly a beta; experimental platform qualifications remain.

## Existing data and database requirements

Item/research IDs, backpack and owner identities, saved-item codecs, database schema,
recipes, machine speeds and energy accounting are unchanged. This is not a schema
migration and does not require deleting or recreating inventories. Old valid item
formats remain readable; the Minecraft 1.21.11 runtime floor is not a saved-data cutoff.

SQLite retains its existing adapter monitor and durability settings. PostgreSQL uses
the transactional batch path. MySQL/MariaDB backpack inventory tables must be verified
InnoDB tables; nontransactional engines are refused rather than saved unsafely. Actual
database tests currently cover MySQL and PostgreSQL, not a separate MariaDB server.
Custom storage adapters must implement the new atomic-save contract. Existing public
methods remain linkable, but unsupported custom adapters explicitly refuse backpack
saves instead of pretending success. Review custom adapters before upgrading.

The fix does not restore previously lost items, remove previously duplicated items,
establish player misconduct, or identify the cause of earlier Albion/Networks reports.
It does not make a transaction across a player's ordinary inventory and a backpack,
two different backpacks, machines, another plugin's storage or multiple servers.

## Addon selection and optional resource pack

This release preserves the complete **45-addon revision 137 source selection**:
Networks **1.0.55**, MagicExpansion **1.1.13**, FluffyMachines **26.2.16**, and the
other 42 maintained selections. The manifest is unchanged. Each versioned release
still requires its own exact-core bundle build and full-stack runtime validation;
unchanged source pins are not a claim that rebuilt JAR/ZIP bytes are identical.

Separately published Networks **1.0.56** and MagicExpansion **1.1.15**, plus their
staged r139/r138 bundle work, remain outside this focused core release. No addon is
silently upgraded, removed or added.
The optional resource-pack source pin and hash remain unchanged. Existing published
4.1.74/r137, r136 rollback and resource-pack assets must not be overwritten.

## Compatibility and historical evidence

The previous published compatibility baseline advances to **4.1.74**, exact source
`4f8aa1e9c288751aeefb9a9f72dbac17a6322b5a`, not current master. Required-addon
regressions block release. The known persistence defect is intentionally fixed; the
older baseline is not being certified crash-safe. The historical 4.1.15 floor remains
advisory, and its older saved-item compatibility is retained.

Source #391 had all 15 PR workflows pass before merging. Its implementation review
recorded 885 core tests with zero failures/errors and one existing skip, four separate
real MySQL/PostgreSQL cases, and seven exact-PR-JAR interruption cases. The post-merge
report for `88e0b1e` separately records the same 885-test total and four real-database
cases. Full source identities, artifacts and limitations are recorded on #391/#390.
These are **historical fix-validation results**, not tests of the new versioned 4.1.75
candidate. Controlled JVM exits and JDBC faults are not hardware power-loss tests or
certification of historical worlds and live Minecraft clients.

Paper 26.3 remains primary, with the existing 1.21.11/26.2 and experimental fork checks.
Java 25 remains the build/current-runtime toolchain and Java 21 the bytecode/1.21.11
floor. **Folia 26.3 expansion is deferred.** No platform target changes in this release.

## Release validation and upgrade checklist

1. Verify the exact versioned candidate with core tests, gameplay/source invariants,
   public API, previous-stable addon compatibility, database, migration and the
   existing platform/runtime matrices. Preserve the failure assertions.
2. Build all 45 pinned addons for that exact candidate and complete the matching
   full-stack two-boot and existing Networks/Fluffy/Black Market runtime probes.
3. Review the exact final source and separately validate the actual merge. Build the
   release JAR twice from the final source and require byte-for-byte equality.
4. Inspect the exact distributable JAR, source/version metadata, test-helper exclusion,
   addon manifest and resource-pack hash. Do not label a 4.1.74 development JAR as
   the new release or replace the old release in place.
5. Publish only through a separately approved, controlled versioned release. Back up
   the full stopped server and database, remove duplicate JARs, start normally and
   verify existing backpacks before and after restart on a staging copy. Never use
   `/reload`, delete data, reset identities or run an unrelated migration as a shortcut.
